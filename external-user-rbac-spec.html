External User RBAC — Specification

This is a dedicated specification for External User RBAC (applicant self-service access to an existing registration), split out from the magic-link email-verification documents it builds on top of. For the underlying email-verification mechanism itself (requesting/resending/verifying a link for a brand-new submission), see magic-link-api-design.md. This document covers only what RBAC adds on top of that.

1. Purpose and scope

Magic-link email verification (see magic-link-api-design.md) proves an applicant owns an email address, for the duration of a single journey, with no lasting session or token. That's sufficient for completing a brand-new submission, but it doesn't let an applicant come back later to view or edit a registration they already made.

External User RBAC is the additive capability that lets them do that: an applicant who already owns a registration (as its primaryContact.contactEmail) can prove that ownership again by magic link, and in exchange receive a short-lived access token scoped to that one registration only.

In scope: entitlement checking (does this verified email really own this registration), issuing/renewing/revoking scoped access tokens, and the two protected endpoints (GET/PATCH /registrations/{reference}) that accept them.

Out of scope: the email-verification mechanism itself (link generation, Notify sending, rate limiting — unchanged, see magic-link-api-design.md); any change to internal (staff) authentication or authorisation.

Relationship to internal (staff) RBAC

This is entirely additive and isolated from staff access. Internal users (case officers, etc.) authenticate via a completely separate auth strategy (entra-bearer, backed by Microsoft Entra / Azure AD) and are unaffected by anything in this document. The two strategies cannot accept each other's tokens — see §4.

2. How entitlement works

Verifying an email address only proves the caller controls that inbox. It does not by itself prove they're entitled to any particular registration. Before any access is granted, the backend performs an explicit entitlement check:

verified email (lower-cased, trimmed)
    ==
registration.primaryContact.contactEmail (lower-cased, trimmed)

This is the only relationship that grants entitlement (see decision §6.1 below) — not any other contact on the registration, such as an additional address's contact.

A failed check — whether because the email genuinely doesn't match, or because the supplied reference doesn't exist at all — returns the identical generic 403 REGISTRATION_ACCESS_DENIED, so a caller can never use the response to learn whether a reference exists or who owns it (see decision §6.6).

3. API contract (addition to POST /email-verifications/verify)

The existing magic-link verify endpoint gains one optional field:

FieldTypeNotes
referencestring, optionalThe registration the applicant wants access to. Omit entirely for a brand-new submission — behaviour is then completely unchanged from the base magic-link design (no entitlement check, no token, no lasting access)

Request

POST /email-verifications/verify
{
  "token": "<the 43-character link token>",
  "reference": "OCR-ABC-123"
}

Response — entitled (200)

{
  "outcome": "VERIFIED",
  "sameJourney": true,
  "externalAccessToken": "<jwt, ~30 minutes>"
}

Response — not entitled (403)

{
  "statusCode": 403,
  "error": "Forbidden",
  "message": "Not authorised to access this registration",
  "code": "REGISTRATION_ACCESS_DENIED"
}

Every other outcome of the underlying link verification (expired, superseded, already used, invalid) is completely unchanged — see magic-link-api-design.md §7.3 / README "POST /email-verifications/verify".

4. The two protected endpoints

EndpointAuthPurpose
GET /registrations/{reference}Authorization: Bearer <externalAccessToken>Read the applicant's own registration, as stored, including its current version
PATCH /registrations/{reference}Authorization: Bearer <externalAccessToken>Update fields on the applicant's own registration (optimistic concurrency via version, same rule as the internal DELETE)

Both are guarded by two independent checks, layered:

  1. Role check (requireExternalUser) — is this a validly-signed external-user token at all? (src/auth/external-bearer-scheme.js)
  2. Record check (requireOwnRegistration) — does the token's own claim name this reference, and does a currently active (not expired, not revoked) grant still exist for it? (src/auth/require-own-registration.js, backed by src/repositories/registration-access.js)

Both must pass. A token that's merely valid is never enough on its own — the persisted grant is re-checked on every request, so a revoked or expired grant can't be used for the remainder of an otherwise-still-valid token's lifetime.

Token shape (src/services/external-user/access-token.js)

ClaimValue
AlgorithmHS256
Issuerpesticides-ocr-backend
Audiencepesticides-ocr-external-user
SubjectThe verified identity (opaque, never the raw email)
referenceThe one registration this token is scoped to
LifetimeexternalUser.tokenTtlSeconds, default 1800s (30 minutes)
SecretEXTERNAL_USER_TOKEN_SECRET (CDP secret). Fails closed if unset — the service cannot issue or verify any token

Deliberately distinct issuer, audience and signing material from the internal Entra tokens, so the two auth strategies (entra-bearer vs external-bearer) can never accept each other's credentials, even by accident — see the dedicated cross-strategy test in src/auth/external-bearer-scheme.test.js.

5. Grant lifecycle (ocr-registration-access collection)

A grant is a persisted record that a given verified identity may access a given registration. It's the thing requireOwnRegistration re-checks on every request — distinct from (but deliberately tied to the lifetime of) the access token itself.

EventEffect on grants
Successful entitlement check (verify + reference)Creates a new grant, or renews an existing one in place (new grantedAt/expiresAt, any prior revocation cleared) — never a duplicate
Grant expiryexpiresAt is set to match the access token's TTL (30 minutes) at the moment of grant/renewal — grant and token expire together
PATCH changes primaryContact.contactEmailEvery existing grant on that registration is revoked immediately, for every identity that ever held one, not just the caller's

An inactive grant (expired or revoked) is treated identically by isPermitted — both mean "not permitted", with no way to distinguish the two from the outside.

6. Design decisions (all confirmed 2026-11-11)

Full rationale for each of these lives in magic-link-tickets.md → "Complete secure applicant access to registrations: decisions confirmed". Summarised here for quick reference:

6.1 Which contact establishes entitlement

Decision: only the registration's own primaryContact.contactEmail. No other contact (e.g. an additional address's) is ever entitled.

6.2 Which routes accept applicants vs staff

Decision: completely separate routes/strategies. No route is genuinely shared between the two populations.

6.3 Grant expiry, revocation and re-verification

Decision: grant and token lifetimes are tied together (30 minutes); re-verifying renews the existing grant rather than duplicating it.

6.4 Effect of a contact-email change

Decision: immediate, unconditional revocation of every existing grant on that registration — no "let the current session finish" grace period.

6.5 Token issuer/audience/algorithm/lifetime

Decision: HS256, distinct issuer/audience from Entra tokens, 30-minute lifetime (intentionally matching the frontend's planned 30-minute session TTL).

6.6 403 vs non-disclosing 404 for denied access

Decision: generic 403 (matches the rest of the API's convention for "authenticated but not allowed"), with an identical body whether the registration doesn't exist or simply isn't the caller's.
