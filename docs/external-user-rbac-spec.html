External User RBAC — Specification

This is a dedicated specification for External User RBAC (applicant self-service access to an existing registration), split out from the magic-link email-verification documents it builds on top of. For the underlying email-verification mechanism itself (requesting/resending/verifying a link for a brand-new submission), see README "API endpoints". This document covers only what RBAC adds on top of that.
Servicepesticides-ocr-backend (API)
Builds onMagic-link email verification (README "API endpoints") — specifically POST /email-verifications/verify
StatusImplemented; all design decisions confirmed (2026-11-11)

1. Purpose and scope

Magic-link email verification (see README "API endpoints") proves an applicant owns an email address, for the duration of a single journey, with no lasting session or token. That's sufficient for completing a brand-new submission, but it doesn't let an applicant come back later to view or edit a registration they already made.

External User RBAC is the additive capability that lets them do that: an applicant who already owns a registration (as its primaryContact.contactEmail) can prove that ownership again by magic link, and in exchange receive a short-lived access token scoped to that one registration only.

In scope: entitlement checking (does this verified email really own this registration), issuing/renewing/revoking scoped access tokens, and the two protected endpoints (GET/PATCH /registrations/{reference}) that accept them.

Out of scope: the email-verification mechanism itself (link generation, Notify sending, rate limiting — unchanged, see README "API endpoints"); any change to internal (staff) authentication or authorisation.

Relationship to internal (staff) RBAC

This is entirely additive and isolated from staff access. Internal users (case officers, etc.) authenticate via a completely separate auth strategy (entra-bearer, backed by Microsoft Entra / Azure AD) and are unaffected by anything in this document. The two strategies cannot accept each other's tokens — see §4.

2. How entitlement works

Verifying an email address only proves the caller controls that inbox. It does not by itself prove they're entitled to any particular registration. Before any access is granted, the backend performs an explicit entitlement check:

verified email (lower-cased, trimmed)
    ==
registration.primaryContact.contactEmail (lower-cased, trimmed)

This is the only relationship that grants entitlement (see decision §6.1 below) — not any other contact on the registration, such as an additional address's contact.

A failed check — whether because the email genuinely doesn't match, or because the supplied reference doesn't exist at all — returns the identical generic 403 REGISTRATION_ACCESS_DENIED, so a caller can never use the response to learn whether a reference exists or who owns it (see decision §6.6).

Order of operations: the entitlement check runs before the one-time link is used up. The backend reads the still-pending link to learn which email it was sent to, then checks the registration. A denied or non-existent reference therefore leaves the link pending, so the applicant can correct a mistyped reference and retry until the link expires. If the link is used and a later step then fails (a changed registration email, a database error while creating the grant, or a token-signing error), the link is put back to pending so a retry still works. This restore is best-effort: if the restore write itself fails, the link stays used and the applicant must request a new one. An already-used, expired, superseded or unknown link is not re-opened and returns its usual error.

3. API contract (addition to POST /email-verifications/verify)

The existing magic-link verify endpoint gains one optional field:

FieldTypeNotes
referencestring, optionalThe registration the applicant wants access to. Omit entirely for a brand-new submission — behaviour is then completely unchanged from the base magic-link design (no entitlement check, no token, no lasting access)

Request

POST /email-verifications/verify
{
  "token": "<the 43-character link token>",
  "reference": "OCR-ABC-123"
}

Response — entitled (200)

{
  "outcome": "VERIFIED",
  "sameJourney": true,
  "externalAccessToken": "<jwt, ~30 minutes>"
}

Response — not entitled (403)

{
  "statusCode": 403,
  "error": "Forbidden",
  "message": "Not authorised to access this registration",
  "code": "REGISTRATION_ACCESS_DENIED"
}

Every other outcome of the underlying link verification (expired, superseded, already used, invalid) is completely unchanged — see README "POST /email-verifications/verify".

4. The two protected endpoints (shared with case officers)

Following PR review (feature/BE-717), these two routes are shared between case officers (Entra) and verified external applicants — not external-only as originally built. An admin editing UI needs the same endpoints case officers already have no other way to reach, so restricting them to externally-verified callers only was a blocker, not a design choice.

EndpointAuthPurpose
GET /registrations/{reference}Authorization: Bearer <entra token> (case officer) or Bearer <externalAccessToken> (applicant)Read the registration, as stored, including its current version
PATCH /registrations/{reference}as aboveUpdate fields on the registration (optimistic concurrency via version, same rule as the internal DELETE)

Both bearer schemes (entra-bearer, external-bearer) read the same Authorization header. Each recognises only its own tokens (by issuer, checked unverified before any signature work) and otherwise reports the token as "missing" rather than "invalid" — so Hapi falls through to try the other strategy. A token that is recognised as that strategy's own, but fails signature/expiry, still gets a real 401. This means a case officer's Entra token and an applicant's external-access token can each only ever be accepted by their own strategy, never the other's, even though the route itself now accepts both.

The route declares both strategies and every role that may call it (requireSharedAccess(), src/auth/require-own-registration.js) — this is the role-level check only. Authorisation is then layered with a single dispatch point, authorise() (src/auth/authorise.js), called from the handler on every request, which branches on identityType ('internal' | 'external', set identically by both bearer schemes):

  1. External caller → requireOwnRegistration (unchanged from the original design) — does the token's own claim name this reference, and does a currently active (not expired, not revoked) grant still exist for it? (backed by src/repositories/registration-access.js)
  2. Internal caller → requireInternalPermission — today a deliberate no-op once the role-level check has passed (any case officer may act on any registration); a placeholder seam for future per-officer/jurisdiction scoping (see open question in §6).

Role alone is still never enough for either population — authorise() must run on every request. A mismatch always returns a generic 403 with no information about whether the requested reference exists.

Token shape (src/services/external-user/access-token.js)

ClaimValue
AlgorithmHS256
Issuerpesticides-ocr-backend
Audiencepesticides-ocr-external-user
SubjectThe verified identity (opaque, never the raw email)
referenceThe one registration this token is scoped to
LifetimeexternalUser.tokenTtlSeconds, default 1800s (30 minutes)
SecretEXTERNAL_USER_TOKEN_SECRET (CDP secret). The service now fails to start outside the local tier if unset, rather than only failing at request time — a missing secret can never turn into a 500 for a caller who has already used up their one-time magic link

Deliberately distinct issuer, audience and signing material from the internal Entra tokens, so the two auth strategies (entra-bearer vs external-bearer) can never accept each other's credentials, even by accident — see the dedicated cross-strategy test in src/auth/external-bearer-scheme.test.js.

PATCH payload: validated against an explicit field schema (unknown(false)), not arbitrary keys. A dotted key such as "primaryContact.contactEmail" is rejected with 400 rather than silently accepted — this matters because it previously could have bypassed the contact-email-change revocation check below, which reads the parsed, nested value. The changes are then merged into the stored registration and the result is validated against the same full schema as POST /register, so cross-field rules still hold (for example, removing seller-amateur without a mainCustomer, or adding use without a quantity, returns 400). A version conflict (VersionConflictError) returns 409.

5. Grant lifecycle (ocr-registration-access collection)

A grant is a persisted record that a given verified identity may access a given registration. It's the thing requireOwnRegistration re-checks on every request — distinct from (but deliberately tied to the lifetime of) the access token itself.

EventEffect on grants
Successful entitlement check (verify + reference)Creates a new grant, or renews an existing one in place (new grantedAt/expiresAt, any prior revocation cleared) — never a duplicate. A unique index on { subject, reference } enforces this at the database level
Grant expiryexpiresAt is set to match the access token's TTL (30 minutes) at the moment of grant/renewal — grant and token expire together. expiresAt is now a required field: a grant can never be created to never expire
PATCH changes primaryContact.contactEmailEvery existing grant on that registration is revoked, for every identity that ever held one, not just the caller's — in the same transaction as the update itself (request.registrations.withTransaction), so a failure part-way through can never leave the old email still holding access

An inactive grant (expired or revoked) is treated identically by isPermitted — both mean "not permitted", with no way to distinguish the two from the outside.

6. Design decisions

Each decision below is stated with its rationale. Re-open any of them only with an explicit, recorded reason.

6.1 Which contact establishes entitlement

Decision: only the registration's own primaryContact.contactEmail. No other contact (e.g. an additional address's) is ever entitled. The comparison is trimmed and lower-cased (services/external-user/entitlement.js).

Rationale: the primary contact is the one field the applicant explicitly nominates as "the person this registration belongs to". Extending entitlement to additional-address contacts would let a third party (e.g. a site manager named only as a delivery contact) gain edit rights to someone else's submission without ever being asked to consent. If shared/delegated access is needed later, it should be its own explicit feature (e.g. an authorisedContacts list), not a side-effect of this check.

6.2 Which routes accept applicants vs staff

Original decision: completely separate routes/strategies, no route genuinely shared.

Superseded (feature/BE-717): GET/PATCH /registrations/{reference} are now shared — both bearer schemes read the same Authorization header and fall through to each other by issuer, with the route declaring both strategies and every role via requireSharedAccess() (role-level), then authorise() dispatching to the correct record-level check by identityType (see §4). The admin editing UI needed the same endpoints case officers already use, so separate routes per population was no longer workable. Each strategy still only ever accepts its own tokens — see §4 for the fall-through mechanics.

6.3 Grant expiry, revocation and re-verification

Decision: grant and token lifetimes are tied together (30 minutes); re-verifying renews the existing grant in place (new grantedAt/expiresAt, any prior revokedAt cleared) rather than duplicating it. A grant can be explicitly revoked (revokeAllForReference); isPermitted treats a revoked or expired grant as not permitted.

Rationale: tying grant lifetime to token lifetime means a persisted grant never outlives every credential that could use it, so a stale grant is harmless by construction. The cost (re-verifying every 30 minutes) is accepted in exchange for not managing two separate expiries. If 30 minutes proves too short, raise tokenTtlSeconds rather than decoupling the lifetimes (but see open question in §6.7).

6.4 Effect of a contact-email change

Decision: immediate revocation of every existing grant on that registration whenever the contact email actually changes — no "let the current session finish" grace period. The new email has no access until it goes through the normal verify flow with the reference and passes the entitlement check again. Revocation runs in the same transaction as the update.

Only a real change revokes: the new and stored emails are compared normalised (trimmed, lower-cased); editing the contact's name or telephone, or re-sending the same email, does not revoke access.

Operational note: PATCH does not verify ownership of a new primaryContact.contactEmail, unlike POST /register. A typo therefore locks the applicant out until the address is corrected, and whoever controls the new address can verify for this reference and gain access. The same applies when a case officer edits the email. Accepted for now; operations should take it into account (for example, confirming a changed address with the applicant out of band).

Rationale: if a session is ever compromised, changing the contact email to one the attacker owns must not give a smooth, uninterrupted continuation of access, as that would turn a one-time entitlement check into no check at all. Letting the current session linger trades a small amount of friction for a real security gap.

6.5 Token issuer/audience/algorithm/lifetime

Decision: HS256, distinct issuer/audience from Entra tokens, 30-minute lifetime (intentionally matching the frontend's planned 30-minute session TTL).

Rationale: the issuer, audience and algorithm are deliberately distinct from the Entra token's so the two strategies can never accept each other's tokens. The 30-minute lifetime is a deliberate match with the frontend session (pesticides-ocr-frontend/external-user-rbac-frontend-changes.md §2.3) so neither side outlives the other. The issuer/audience strings are internal detail; nothing downstream pins to their literal values.

6.6 403 vs non-disclosing 404 for denied access

Decision: generic 403 (matches the rest of the API's convention for "authenticated but not allowed"), with an identical body whether the registration doesn't exist or simply isn't the caller's.

Rationale: 403 and a non-disclosing 404 are equally safe provided the body never varies by reason. The only question was consistency with the rest of the API, which already uses 403 for "authenticated but not allowed". This matches the frontend design (pesticides-ocr-frontend/external-user-rbac-frontend-changes.md §2.5), so no frontend change is needed.

6.7 Open questions raised by sharing the routes (feature/BE-717, not yet confirmed)

Sharing GET/PATCH /registrations/{reference} between populations surfaced questions not covered by the original 2026-11-11 decisions, flagged here for the team rather than decided unilaterally:

  • Role naming: requireSharedAccess() currently lists the external role alongside the existing case-officer role names (see getCaseOfficerRoles()) — is a dedicated "can access shared routes" scope/claim warranted instead of reusing the population-specific role lists directly?
  • Editable fields per population: patchSchema is currently identical for both populations. Should case officers be able to edit fields an applicant cannot (or vice versa), e.g. internal-only status/jurisdiction fields?
  • Grant/token lifetime: still 30 minutes, matched to the frontend's planned session TTL (§6.5) — does that still make sense now the same token can be used from an admin-style editing flow, which may run longer than an applicant's single session?
  • Internal jurisdiction scope: requireInternalPermission (src/auth/require-own-registration.js) is a deliberate no-op today — any case officer may act on any registration once role-level access passes. Is per-officer or per-dataset scoping needed before this ships more broadly?
  • Follow-up ticket — one verification per registration: the unique index on {subject, reference} (§5) assumes a single active grant per identity/registration pair is always sufficient; worth a follow-up ticket to confirm this holds once case officers are also issuing/consuming grants on the same records.
